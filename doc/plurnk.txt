1. Setup                                                         *plurnk-setup*

Requires Neovim >= 0.10 and a running plurnk-service daemon (default
127.0.0.1:3044). An optional `plurnk` executable on PATH supplies shared GFM
and Beautiful Mermaid presentation; without it, Markdown remains source. >lua

  require("plurnk").setup({ host = "127.0.0.1", port = 3044 })
  require("plurnk").apply_default_keymaps()  -- only fills unmapped keys
<

`:checkhealth plurnk` reports the installed checkout/version, redacted daemon
endpoint, AG-UI+ compatibility, optional renderer, and every enabled default
mapping. Occupied keys are preserved; setup emits one aggregate warning and
health identifies their owner when Neovim exposes it.

2. The :AI language                                       *plurnk-ai* *:AI*

`:AI/` prints the compact grouped command index; `:AI/help {verb}` prints one
command's exact usage and purpose. Routing, completion, help, and default key
descriptions consume the same registry. No-space forms (`:AI?? hi`) work via
cmdline abbreviations.

  :AI               toggle workspace tab <-> where you came from
  :AI {text}        prompt (act)
  :AI? {text}       ASK: read-only loop (flags.mode="ask"; the daemon
                    403s schemes excluded in ask — file edits, exec)
  :AI: {text}       act (the default)
  :AI! {cmd}        exec {cmd} via the daemon; bare :AI! execs the
                    visual selection verbatim
  :AI?? / ::        new workspace, then prompt
  :AI???            new headless workspace (no project root)
  :AI????           new worker in the current workspace (fork)
  :AI... {text}     inject into the running loop
  :AI/              show the grouped command index
  :AI/help {verb}   show exact contextual usage

Visual mode prepends the selection: `'<,'>AI? explain this`.

Completion demand-loads model aliases, reasoning policies, local paths, and
the current Worker's MCP, Skill, or A2A aliases only where the command consumes
them. `/open`, `/reconnect`, `/next`, `/prev`, and `/clear` are deliberate
editor-native controls; other command vocabulary follows the terminal client.

3. Layout: workspaces and workers                               *plurnk-layout*

A WORKSPACE is the world (project root, entries, persona). A WORKER is a
conversation within it; the waterfall is the worker's log — exactly what the
model sees. One tab per worker by default; buffers are named
`plurnk-nvim://<workspace>/<worker>` so any window arrangement works with vim's own
machinery.

One workspace is live per Neovim instance. Switching workspaces (or workers)
rebinds the connection in place and notifies; a loop mid-flight continues on
the daemon (and still completes) — you just stop seeing its live events, so
the notify says to reopen the worker to catch up.

The input split (bottom, 3 lines): `<CR>` in normal mode submits. Prefixes
match :AI — `? ` ask, `: ` act, `! ` exec; `# PLAN0` / `## OP0` enter raw
PLURNK.

Readable provider reasoning appears before its SEND as a distinct `💭` block.
Multiline reasoning begins in a native closed fold. PLAN remains the model's
durable working-memory inventory: ✅ completed, 🚧 in progress, 💾 memory,
⬜ pending.

Each model body is independent, so its Markdown never styles later Plurnk rows.
When `plurnk render` is available, tables wrap with horizontal row separators,
task markers render once, code fences retain a `💻 language` header, and Mermaid
is projected through Beautiful Mermaid. The source entry stays authoritative;
without the optional renderer, it remains visible verbatim.

4. Proposals                                                 *plurnk-proposals*

Side-effecting ops pause for review. EDIT opens a diffsplit (left = disk,
right = proposed):

  <localleader>a    accept as proposed
  <localleader>e    accept with your edits (udiff regenerated)
  r                 reject
  c                 cancel

EXEC opens a scratch: `a` / `r` / `c`. From anywhere: `<leader>ay` accept,
`<leader>ae` accept-with-edits, `<leader>an` reject, `<leader>a]` / `a[`
cycle pending. `:PlurnkYolo` auto-accepts everything.

==============================================================================
5. Streams                                                     *plurnk-streams*

Exec output streams into a split below the waterfall: `1|` stdout,
`2|` stderr (highlighted). The winbar shows the stream URI; a footer and a
HUD toast mark conclusion. Wiping a live stream buffer cancels the
subscription with status 499.

==============================================================================
6. Statusline                                               *plurnk-statusline*
>lua
  vim.opt.statusline = "%f %{v:lua.require('plurnk').statusline()} %l/%L"
<
The statusline is one live state glyph. The worker winbar owns the rich
snapshot, for example `plurnk · workspace · worker · 🤖 alias · 🧠 adaptive
· L3·T2 · ⏹️ · ↑12.3k ↓420 · ctx 15%/49k · loop: $0.0042`. Input/output, context, and the
exact decimal or unknown cost all come from the last loop's terminal accounting
envelope; they are never a client-computed workspace total.

==============================================================================
7. Architecture                                           *plurnk-architecture*

  Neovim  -- AG-UI+ HTTP/SSE -->  plurnk-service

Neovim consumes the daemon's AG-UI+ HTTP/SSE interface through curl. The
external protocol contract lives in the plurnk-agui SPEC.
Model Markdown may independently use the optional local `plurnk render`
stdin/stdout filter; protocol traffic never does.
One live workspace per instance; switches rebind the connection in place.
Tests: `./tests/runner.sh` boots a private daemon (tmp DB, ephemeral port)
from the sibling checkout; `PLURNK_SERVICE_DIR` overrides; `PLURNK_PORT`
targets an existing daemon.
